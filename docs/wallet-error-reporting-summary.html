Error handling for wallet app integrators

When a wallet flow fails (issuance, presentation or DC API), the failed KmmResult holds one of a small set of documented exception types. This page lists them, in the order to check them, with what to tell the user.

Decide on the type, never on the message.

Exception messages are English text for developers, meant for logs and bug reports. They may change in any release and are never meant to be shown to users.

Classify a failure: check top to bottom

Take result.exceptionOrNull() and stop at the first type that matches. The user messages are suggestions for the app to word and localize. Where a type carries data, such as dates or the issuer, use it to make the message more specific. Validation reports of credentials (prepareCredentialStorage) and of presentation requests (startAuthorizationResponsePreparation with a policy) are not failures: they are returned as values, to show before the user decides.

Validation reports: show them, then let the user decide

Before the wallet stores a credential or answers a verifier, VC-K validates what it received and returns a ValidationReport: every check with its outcome, and an overall decision under the ValidationPolicy the app passed. A rejected report is not a failure: the call succeeds, and the app shows the report and decides with the user.

Issuance

OpenId4VciKtorClient.loadIssuerMetadata(issuer, policy)
Signed issuer metadata: LoadedIssuerMetadata.Signed.validation.report. Show untrustedRegistration only marked as unverified.
CredentialIssuanceResult.Success.prepareCredentialStorage(holder, policy)
Each received credential: PreparedCredentialStorage.validation.report. Also on HolderAgent.prepareCredentialStorage.

Presentation

OpenId4VpKtorHolder.startAuthorizationResponsePreparation(input, policy)
The verifier's request: AuthorizationRequestValidation.validationReport, and its relying party in relyingParty. Show relyingParty.untrustedRegistrations only marked as unverified.
OpenId4VpKtorHolder.prepareDcApiRequest(request, policy)
The same for a request over the Digital Credentials API: DcApiRequestValidation.

From a thrown error

ValidationException.Rejected.report
When an operation needs an accepted report and gets a rejected one, the report comes with the error. Show it the same way.

How reports relate to errors

Report (returned)

  • The call succeeds; decision is ACCEPTED or REJECTED.
  • A check that didn't pass holds its reason as CheckOutcome.Failed(throwable) or Blocked(cause); read it with outcome.cause().
  • The user may accept what the policy lets them: an untrusted issuer, an expired or revoked credential, missing claims.
⇄
same exception types, same user messages

Error (thrown)

  • The KmmResult fails.
  • The reasons are the same ValidationException subtypes as in reports: Timeliness, TokenStatus, MissingRequiredClaims, RelyingParty.*, ...
  • Happens only when the app goes on without an accepted report, or the user can't accept it: ValidationException.Rejected carries the report.

So one function that turns a ValidationException into a user message serves both: the causes inside a report and the errors in the table above.

Storing a credential: three outcomes

Accepted

report.decision == ACCEPTED. Store it with HolderAgent.storeAccepted, no question needed.

Rejected, but intact

validation.unacceptedCredential != null: e.g. an untrusted issuer, expired, revoked, or missing claims. Show the report; if the user accepts, store it with storeAfterUserConsent.

Not intact

e.g. an invalid signature or bound to another key. No user can accept it, so storeAfterUserConsent fails with ValidationException.Rejected. Explain why it can't be stored.

How to display a report

  • ValidationReport — decision: the headline, accepted or rejected
    • checks — the typed checks of this artifact, e.g. CredentialChecks, RequestObjectChecks
    • namedChecks — each check by name, with its requirement, outcome and satisfied
      • PassedFailedBlockedNotApplicable
      • data for the message: trust (trust source), statusMechanism (observed status), claims (missing claim paths), outcome.cause()
    • children — nested reports, e.g. status list tokens, the relying party and its certificates, presented credentials
  1. Headline from decision. Accepted: nothing to ask. Rejected: show what didn't pass.
  2. List every check that is not satisfied, in this report and, recursively, in its children.
  3. Tell Failed from Blocked. Failed: the check ran and failed ("The issuer is not trusted"). Blocked: it couldn't run, e.g. the status list was unreachable or the wallet has no trust anchors for this type ("The status could not be checked").
  4. Key labels by the type of checks and the check's name. Names are field names, e.g. issuerTrust, timeliness, status.mechanisms[0]; a rename is a breaking change in the CHANGELOG.
  5. Show OPTIONAL checks as notes: they never change the decision.
  6. Never expect claim values in a report. Reports name claims by path only; show values from the credential itself.
Example: issuance (Kotlin, with the types of 10.0.0)
// After the redirect back from the authorization server
val success = vciClient.resumeWithAuthCode(redirectUrl, context).getOrThrow()
val prepared = success.prepareCredentialStorage(holderAgent, policy).getOrThrow()

for (credential in prepared) {
    val validation = credential.validation
    when {
        validation.report.decision == ValidationDecision.ACCEPTED ->
            holderAgent.storeAccepted(credential)
        validation.unacceptedCredential != null ->   // untrusted issuer, expired, revoked, ...
            if (askUser(findings(validation.report))) holderAgent.storeAfterUserConsent(credential)
        else ->                                       // not intact: can never be stored
            showCannotStore(findings(validation.report))
    }
}
Example: presentation
val validation = vpHolder.startAuthorizationResponsePreparation(requestUrl, policy).getOrThrow()
showRequest(
    findings = findings(validation.validationReport),
    registrations = validation.relyingParty?.untrustedRegistrations.orEmpty(), // mark as unverified

// User agrees:
vpHolder.finalizeAuthorizationResponse(validation.preparationState, presentation)
// User declines (OpenID4VP 1.0, 8.5: access_denied):
vpHolder.sendAuthnErrorResponse(OAuth2Exception.AccessDenied("declined by the user"), validation.preparationState)
Example: findings and their messages
// One finding per check that is not satisfied, in this report and its children
data class Finding(val checks: ValidationChecks, val check: NamedCheck)

fun findings(report: ValidationReport): List<Finding> =
    report.namedChecks.filterNot { it.satisfied }.map { Finding(report.checks, it) } +
        report.children.flatMap { findings(it) }

// The same messages as for thrown errors, from the cause of the check
fun Finding.userMessage(): String = when (val cause = check.outcome.cause()) {
    is ValidationException.Timeliness ->
        cause.notAfter?.let { "Expired on $it." } ?: "Not valid yet."
    is ValidationException.TokenStatus -> "Revoked or suspended by its issuer."
    is ValidationException.MissingRequiredClaims -> "The credential is incomplete."
    is ValidationException.RelyingParty.UnregisteredRequest -> "Not registered to request this data."
    else -> when {
        check.outcome is CheckOutcome.Blocked -> "Could not be checked."
        check.trust != null -> "Not trusted."           // trust, issuerTrust, signerTrust
        else -> "The credential did not pass a check." // log check.name
    }
}

Why documented types, and not checked exceptions

No compiler, Kotlin or Swift, can force an app to handle every failure of a wallet flow. What VC-K offers instead: a small set of sealed root types, a list of them in the KDoc of every entry point, and tests that keep that list true.

Kotlin has no checked exceptions

No Kotlin signature can declare "fails only with these types", and the compiler checks no catch. @Throws only changes how a function is exported to Java and Objective-C.

Swift only sees untyped errors

Swift reaches VC-K through Kotlin/Native's Objective-C export. A Kotlin function annotated with @Throws becomes a Swift throws function, but the error is an NSError that wraps the Kotlin exception, never a specific type. Swift 6 has typed throws, but Objective-C has no equivalent, so the export can't produce them. An exception whose type is not listed in @Throws terminates the app. That is why VC-K returns KmmResult: Swift always gets a value, never a crash, and casts the failure with as?.

Sealed doesn't reach Swift

A sealed Kotlin class is exported as an ordinary class hierarchy, with nested classes flattened into names like OAuth2ExceptionAccessDenied. Swift can't switch over it exhaustively. Kotlin callers get exhaustive whens once they've narrowed to a root, e.g. ValidationException.

A typed error channel still needs a catch-all

A Result<T, WalletError> would force VC-K to wrap network errors, the user cancellation and bugs into its own type. That would hide the types apps need most, and the type would still need an "anything else" case, so the app would gain no exhaustiveness.

The protocols are open-ended

OAuth, OpenID4VCI and OpenID4VP allow error codes that aren't defined yet. OAuth2Exception needs Other(error), and any when over it a branch for that.

What you can rely on

  1. The type of the failure, checked from the root types down, as above.
  2. The KDoc of each entry point, which lists the types it fails with.
  3. The CHANGELOG, which marks every change of that list as BREAKING.
